# Roadmap workflow

Use the connected roadmap MCP tools. The host agent supplies reasoning, web research and a clean-context reviewer; the plugin supplies persistent state, validation and reusable rendering. No model API key is needed. Never invent a check, source fragment, attachment or reviewer.

1. Call `roadmap_start` with facts the user already supplied. Preserve the user's goal and DoD; do not substitute a career direction. Do not reconfirm facts from the current chat. Facts from old chats require confirmation. If DoD is absent, derive it later from the goal; do not demand it from the user.
   Planning is always effort-only: estimate approximate hours for steps, practice, stages and the mandatory route, with reserve stated separately. Do not ask for or calculate a personal schedule, weekly budget, or completion deadline. Practical constraints such as equipment, money, access and materials remain relevant; personal time mentioned in free text is not a planning constraint. Legacy schedule fields remain readable history and are never used for planning. Do not seed retired fields; new writes to them are rejected as unknown fields.
2. Call `roadmap_question` after starting/resuming an incomplete session. EVERY question must use interactive input, including questions after the first. Native MCP elicitation continues through all remaining questions inside the tool, displaying one form at a time. If it returns `mode=host-ui`, follow its `inputMode` and input instructions, save the actual answer through `roadmap_answer`, then call `roadmap_question` again; repeat until `inputComplete=true`. The six active questions are goal, level, practical constraints, priorities/exclusions, output format and destination. Only output format has predefined choices; show its supplied human-readable labels. All other questions use free text; do not invent answer buttons or placeholders. Include supplied hints. If a host question tool requires nonempty choices for an open field, use a free-input form instead; only when no suitable interactive input exists, explain the limitation and ask that field in chat. A `nextQuestion` in a start/answer/get response is state metadata, not an instruction to repeat it in chat. Missing MCP elicitation alone does not mean missing host UI. Never treat cancellation as an answer. Skip already supplied answers.
3. Read [curriculum](references/curriculum.md) and [sources](references/sources.md), available through `roadmap_guidance`. Read [data conventions](references/data.md). Load `roadmap_schema` only for the object being authored. Form the competence model and independently derive scenarios from the goal, then cross-check both ways. Define the stage DAG before detailed authoring. Estimate hours and uncertainty from the actual work; do not convert them into dates or calendar duration.
4. Upsert one object at a time with `roadmap_put`; keep a stable author context ID. Fill stages fully, checking source fragments before advancing. Use host search/open tools: the MCP server does not browse or assess teaching sufficiency. Mandatory route: free, legal, Russian/English materials, an authoritative theory source and external practice source per stage. Paid books only as optional additions/alternatives; no other paid materials. If a resource cannot be checked, record the limitation and source gap. Do not declare the route confirmed.
5. Run `roadmap_validate`, fix structural failures and perform the author's content audit. Structural checks cannot prove educational quality. Before review, read `roadmap_guidance(phase=editorial)` and complete its separate full-roadmap clarity/executor pass A and content-preserving proofreading pass B, including resumed and repaired sessions. Record factual coverage before preparing review. Read [rubric](references/rubric.md) and [review](references/review.md) at the review phase. Use `roadmap_prepare_review`; pass its file unchanged to a separate reviewer in a fresh context, with no author self-score or previous verdict. Ask the reviewer to return the `review` schema and actual evidence. Submit through `roadmap_submit_review`. The independent flag is an attestation, not proof of context isolation; the host must really create a separate context.
6. Repair findings and reassess in a fresh context, at most three repair cycles after the initial assessment. Never adjust scores yourself. If no separate reviewer is available, provide the packet for another session and label the result preliminary. Self-review does not confirm the ≥85 threshold. Best-effort preliminary artifacts remain allowed and must expose remaining limitations. Do not delay the requested output merely to force a passing score.
7. Read [delivery](references/delivery.md), call `roadmap_build`. Offer exactly these delivery choices: **interactive local website (ZIP)**, **PDF document**, or **both**. Internal `format=html` means a complete multi-page interactive local website with DAG, separate stage pages, search, themes and progress, packaged as a sibling ZIP archive; it never means a single standalone HTML document. Use the built-in renderer and return the archive path from `artifacts.htmlArchive`. Inspect screenshots returned in `diagnostics.screenshotsDirectory` and visually inspect PDF pages using host tools. Report only checks actually completed. Fix rendering defects in reusable code, not by shortening content. A real content defect requires revising the data, a new review where affected, and rebuilding both formats. Return the selected artifacts and whether content review and visual QA are complete.

Resume by session ID and `roadmap_get`. Read individual changed objects instead of repeatedly loading the whole program. State is stored outside installed package resources. Do not regenerate HTML/CSS/JS for each roadmap. Do not send messages, publish, or install anything merely because this skill is active.
