# Roadmap workflow

Use the connected roadmap MCP tools. The host agent supplies reasoning, web research and a clean-context reviewer; the plugin supplies persistent state, validation and reusable rendering. No model API key is needed. Never invent a check, source fragment, attachment or reviewer.

1. Call `roadmap_start` with facts the user already supplied. Preserve the user's goal and DoD; do not substitute a career direction. Do not reconfirm facts from the current chat. Facts from old chats require confirmation. If DoD is absent, derive it later from the goal; do not demand it from the user.
2. Call `roadmap_question`. Ask exactly one pending question at a time. Prefer native elicitation when supported, otherwise use the host's interactive question UI or chat. Include hints and choices; allow free text where appropriate. Save actual answers via `roadmap_answer`; a cancellation is not an answer. Questions cover goal, level, weekly hours, deadline, constraints, priorities/exclusions, output format and destination. The last two are output preferences, separate from the source prompt's maximum seven clarification questions. Skip already supplied answers.
3. Read [curriculum](references/curriculum.md) and [sources](references/sources.md), available through `roadmap_guidance`. Read [data conventions](references/data.md). Load `roadmap_schema` only for the object being authored. Form the competence model and independently derive scenarios from the goal, then cross-check both ways. Define the stage DAG before detailed authoring. If time is insufficient, retain necessary practice, explain the mismatch and give realistic duration plus an interim outcome.
4. Upsert one object at a time with `roadmap_put`; keep a stable author context ID. Fill stages fully, checking source fragments before advancing. Use host search/open tools: the MCP server does not browse or assess teaching sufficiency. Mandatory route: free, legal, Russian/English materials, an authoritative theory source and external practice source per stage. Paid books only as optional additions/alternatives; no other paid materials. If a resource cannot be checked, record the limitation and source gap. Do not declare the route confirmed.
5. Run `roadmap_validate`, fix structural failures and perform the author's content audit. Structural checks cannot prove educational quality. Read [rubric](references/rubric.md) and [review](references/review.md) at the review phase. Use `roadmap_prepare_review`; pass its file unchanged to a separate reviewer in a fresh context, with no author self-score or previous verdict. Ask the reviewer to return the `review` schema and actual evidence. Submit through `roadmap_submit_review`. The independent flag is an attestation, not proof of context isolation; the host must really create a separate context.
6. Repair findings and reassess in a fresh context, at most three repair cycles after the initial assessment. Never adjust scores yourself. If no separate reviewer is available, provide the packet for another session and label the result preliminary. Self-review does not confirm the ≥85 threshold. Best-effort preliminary artifacts remain allowed and must expose remaining limitations. Do not delay the requested output merely to force a passing score.
7. Read [delivery](references/delivery.md), call `roadmap_build`. Inspect screenshots returned under `qa/` and visually inspect PDF pages using host tools. Report only checks actually completed. Fix rendering defects in reusable code, not by shortening content. A real content defect requires revising the data, a new review where affected, and rebuilding both formats. Return the selected artifacts and whether content review and visual QA are complete.

Resume by session ID and `roadmap_get`. Read individual changed objects instead of repeatedly loading the whole program. State is stored outside installed package resources. Do not regenerate HTML/CSS/JS for each roadmap. Do not send messages, publish, or install anything merely because this skill is active.
