# Architecture and decisions

## Boundaries

The host agent owns goal interpretation, curriculum synthesis, browsing, source sufficiency judgment, independent-review orchestration and visual inspection. The MCP server is a local deterministic toolkit: intake, persistent JSON sessions, schema checks, evidence traceability, score arithmetic, export and browser smoke audit. It makes no LLM calls, has no credential store and does not claim that a status string proves learning or source correctness.

The same core functions serve MCP and CLI. Local stdio avoids a daemon, listening port, authentication service and a hosted dependency. Remote-only clients need a future HTTP deployment; stdio is the supported portability boundary for v0.1.

## State and invariants

- Each session has a UUID and is stored under a configured writable data directory, separate from installed package assets.
- JSON writes use temporary-file + rename; operations on one session are serialized in one server process. Do not run multiple processes against the same session concurrently (no distributed lock).
- Collection upserts touch one object; removing an object does not silently remove dangling references.
- Stage IDs cannot become paths. Export folder names use a single sanitized NFC title (goal fallback), UTC date and random suffix helper; diagnostics use an unrelated build UUID. Titles are never used without this controlled transformation.
- One required final stage, acyclic prerequisites, all required stages are ancestors of the final stage. Optional branches cannot be prerequisites of a required stage.
- The full selected artifact set is staged and machine-checked before destination writes. Publication uses exclusive creation and copies verified bytes into a safely named new directory/sibling ZIP; existing exports are never overwritten. Diagnostics remain under a separate build-UUID directory.
- Markdown is sanitized; scripts, event handlers, remote images and unsafe protocols are removed. No model-generated JavaScript is executed by the renderer.
- Source status is recorded evidence, not a proof generated by software. Exact checked fragments and evidence links are required for confirmed mandatory routes.
- Review is bound to canonical SHA-256 of roadmap + input answers. A changed answer/content makes the old review stale. Scores use unchanged weights and integer levels. Old evaluations are omitted from review packets; free prose must still be checked by the author for embedded prior judgments.
- Reviewer identity/context/independence are host attestations. Server cannot observe model context isolation. No fabricated second reviewer.
- The build reads one in-memory snapshot for HTML, PDF and exported JSON. The host must not mutate that object during build; Store serializes tool mutations while a build is active.

## Rendering and checks

HTML uses classic local scripts and static pages, compatible with file://. DAG layout uses topological layers with optional branches and preserved edges. Long edges route through the outer lane. Search index is prebuilt. Local progress has a roadmap-specific namespace, supports import/export and degrades without storage. It never changes program evaluation. Authoring and review use the separately loaded editorial reference for distinct full-text clarity and proofreading passes; the server does not claim to verify their semantic completion.

PDF uses Chromium's print engine with the same content functions and print CSS, local system fonts and no network resources. HTML and extracted ZIP audits, archive inventory checks and PDF DOM/file-marker smoke checks run in local staging before destination publication. Saved screenshots are evidence for a later visual inspection, never an automatic claim of visual success. ZIP/PDF checks do not certify semantic quality or visual readability.

## Cost control

Only load instructions for the active phase, read/update one object, store sources once, generate repeated short cards and both presentation formats in code. Mechanical checks do not call a model. Fresh-context reviewers receive the required packet once per assessment; no cheaper-model routing is implemented.

## Native OpenCode adapter

`integrations/opencode/index.js` is the root package export for OpenCode V2. Its native setup registers the existing MCP server through a transform, the packaged skill with its real base path, and `/roadmap` with a prompt-preserving command handler. Cleanup disposes registrations in reverse order; partial setup failure rolls back completed registrations. No SDK dependency, model routing, provider/auth changes or global config writes are added. OpenCode runs on Bun, so its `process.execPath` must not be used as Node.js: the adapter uses `node`, ROADMAP_NODE_PATH or the explicit nodeCommand option.

OpenCode 2.2.5 was tested with the singular `plugin` array of string paths, despite newer documentation showing plural `plugins`. CLI config generation provides the tested form by default and `--modern` for the newer documented form. Root opencode.json makes opening this repository sufficient for native loading. Manual matching MCP settings are preserved; conflicting server/skill names cause an explicit error. Windows file URLs are used for generated config entries.

`npm run test:opencode` starts the installed OpenCode in an isolated XDG configuration/data/cache/state environment, loads the plugin, authenticates to its owned localhost server and checks actual plugin/skill/command/MCP registries. It never submits a model prompt and does not alter user configuration. In-process tests additionally check command attachments, delivery, conflicts, cleanup, options and the generated stdio launch command.

## Deferred capabilities

Remote HTTP/OAuth, model routing/API orchestration, automatic semantic source verification, LMS analytics, real learner assessment, cloud file storage and public marketplace publishing are outside v0.1. None is necessary for local reusable generation.
